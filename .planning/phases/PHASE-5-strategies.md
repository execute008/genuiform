# Phase 5 — Strategies

## Goal

Build the two concrete `Strategy` implementations that drive the form turn-by-turn: `GenerativeStrategy` (every step generated by the LLM, schema-constrained) and `GuidedStrategy` (the LLM picks the next step from a developer-supplied catalog of `QuizStepSpec`). Both consume `Session` + `FormConfig` and emit a `Stream<StepEvent>`. Both go through `ConstraintEnforcer`, `OutcomeNavigator`, and `EngagementReader`. **All tests use `FakeLlmClient` — zero real network calls.** Per the hackathon priority list, `GenerativeStrategy` is the §13.1 must-have; `GuidedStrategy` can land last in this phase if time pressure mounts.

## Acceptance criteria

### Shared
- [ ] `Strategy` abstract class matches spec §8 exactly: `Stream<StepEvent> nextStep(Session session, FormConfig config);`
- [ ] `FormConfig { required Contract contract; required List<Constraint> constraints; required Posture posture; required OutcomeNode outcomes; required LlmClient client; required String model; double temperature = 0.7; List<QuizStepSpec>? guidedCatalog; }` — frozen, equatable.
- [ ] Streaming strategy errors are surfaced as `StreamError` events, never thrown.

### `GenerativeStrategy`
- [ ] Builds the §10.1 system prompt from `FormConfig` (contract, constraints, posture, outcome tree, history, engagement).
- [ ] Calls `client.generate(systemPrompt, messages, responseSchema, model, temperature)`.
- [ ] Parses the returned JSON against the `decision` discriminator from spec §10.2 and emits the corresponding `StepEvent`:
  - `decision == 'ask_step'` → `StepReady(spec)` after `ConstraintEnforcer.check` (which may swap the spec).
  - `decision == 'offer_exit'` → `LayerComplete(layer, offerExit: true)` plus a `StepReady(exitOffer)` if `exit_offer` is present.
  - `decision == 'resolve_branch'` → `BranchTaken(branchId, optionId)` after `OutcomeNavigator.advance`.
  - `decision == 'complete'` → `OutcomeReached(outcome, FormResult(...))` after computing the final `FormResult`.
- [ ] Reads `engagement` from the response and feeds the next prompt via `EngagementReader.combine` with the heuristic backend.
- [ ] Honours `MaxSteps` and `MinSteps` constraints by aborting the stream / refusing premature completion.
- [ ] Buffers streaming text until valid JSON before parsing (defers per spec §15 open question).
- [ ] On `EscalateIf` match (via `ConstraintEnforcer.inspectAnswer` against the previous answer), emits `EscalationFired` and stops the stream.

### `GuidedStrategy`
- [ ] Receives `guidedCatalog: List<QuizStepSpec>` via `FormConfig`.
- [ ] On each turn: if there are unanswered required fields, calls the LLM with a "pick the next step id from this catalog" schema (single-key JSON: `{ "next_step_id": "..." }`), then emits `StepReady` for the matching catalog entry.
- [ ] If all required fields are satisfied, advances `OutcomeNavigator` and emits the appropriate event.
- [ ] Same constraint-enforcement and engagement-reading wrapper logic as `GenerativeStrategy`.
- [ ] Latency is dominated by the LLM call but the LLM workload is much smaller (no step generation, just a routing decision) — assert in the test that the system prompt is significantly shorter (< 1500 chars) than `GenerativeStrategy`'s.

## Test strategy

- **Every test uses `FakeLlmClient` from Phase 3.** No `MockClient(http)`, no real network.
- Prompt-builder test: deterministic golden string — when the prompt template changes, the test fails on purpose so a human reviews the diff.
- Use `expectLater(stream, emitsInOrder([...]))` from `package:test` for stream-based assertions.
- Coverage target: each `decision` discriminator value, each constraint variant interaction, each engagement signal value.
